Learn by making

18 practical studio lessons with explanations, practice, troubleshooting and knowledge checks.

Practice beside your project#

Open Learn → Studio learning paths. Choose any studio and lesson. Read the explanation, try the three steps and answer the knowledge check. The existing eleven Lua lessons are still in the sidebar.

Open … · keep lesson beside me opens the workspace with a collapsible practice panel. Project creation uses the normal dialog; no project is silently replaced. Return to the lesson to finish the knowledge check.

Progress is saved on this PC, separately from projects, backups and cloud snapshots. Checkboxes are your own practice record, not automatic build or in-game verification. Lessons never lock professional features. Find the tools and character sources first if you need setup.

Clothing Studio#

Meet your real GTA character

Choose a male or female freemode character and identify the garment you will edit.

The body is your fitting reference; the garment is the item you change. A model supplies shape and UV coordinates. A texture supplies the colors printed on that shape. Picking the matching body first prevents designing for the wrong fit.

Freemode ped: The customizable GTA character. Male and female use different bodies and compatible clothing.

  1. Open Tools & models in Learn and follow the Blender, Sollumz and CodeWalker setup. Keep your GTA V Legacy installation available.
  2. Open Clothing Studio, choose Tops, T-shirts & hoodies and choose Male or Female under Fitting body. Click Set up GTA character and select your own GTA V Legacy folder when prompted.
  3. Use Front, Side and Back to inspect the loaded character. For another item, use Edit GTA clothing, choose a drawable and its original texture, then Edit selected GTA item. If a garment is already linked, read Change and keep artwork before switching.

Expected result: A real local character and garment appear. The male or female selection matches your intended wearer. Setup is cached on this PC; other PCs need their own game files and setup.

If it does not work: If setup fails, use Check installed tools. Select the Blender installation that has Sollumz enabled. Choose the Legacy folder containing GTA5.exe and x64v.rpf. A filename typed into a GLB dialog is not an existing model.

Why choose the fitting body before designing?

The garment must fit the intended body. A design can look correct on one body and clip on another. The body choice is part of the asset target.

Try independently: Locate the Female option and explain which setup would need repeating on a second PC. You do not need to switch your current design.

Recolor a shirt and place a logo

Change a fabric color and position your own artwork while understanding UVs.

The artwork canvas is a flat texture. UV coordinates tell the app which pixels belong on the chest, sleeves and back. A rectangle that looks centered on the canvas may cross a seam on the actual garment. Check the 3D result after each change.

UV: The mapping between a flat image and the surface of a 3D mesh.

  1. Select your garment material for painting. In Design, click the Fabric color swatch and choose a color. For black use #101010. If an original diffuse image covers it, inspect the artwork layers: an opaque image can hide the color underneath.
  2. Choose Add text and enter a short word, or Add PNG for your own transparent logo. Select that layer and drag it on the artwork canvas. Use its size controls or resize handles to fit it within the chest area.
  3. Enable UV seams when working on an imported garment. Check Front, Side and Back; move the artwork away from seams or unintended surfaces. Undo one change and redo it to learn the recovery controls.

Expected result: The selected garment shows the intended color and readable artwork. Changing the design does not recolor the body or every material in the scene.

If it does not work: If color does not change, check the selected Paint material and whether an original image layer covers it. If the logo repeats or stretches, inspect the UV layout; shrinking the image cannot repair shared or distorted UVs.

A logo is split across the chest and sleeve. What should you inspect?

The UV layout and artwork placement. The texture is being mapped to multiple surface regions. Their UV boundaries determine the placement.

Try independently: Create a second layout with smaller lettering. Compare both in 3D, then keep the one you prefer.

Save a design and choose an export

Distinguish an editable project, a PNG and a wearable resource.

Saving the project preserves the editable layers. Export PNG texture makes an image, not a game-ready garment. A native wearable needs the correct model, matching textures and resource setup. Retexturing an existing item and building a new wearable are different workflows.

YTD: A GTA texture dictionary containing named texture entries used by a model.

  1. Wait for Saved, then use Project backup to keep a separate editable copy. Reopen the project from Projects and confirm the lettering and colors are still editable.
  2. Export PNG texture to a working folder. For a supported existing GTA garment, save its original texture dictionary and use GTA texture dictionary → Retexture existing YTD to save an edited copy. Keep the original source.
  3. Open Pack Builder for a wearable resource. Select the correct body and item slot, supply the required native or prepared source files and run its checks. Stop at any unresolved build requirement; a PNG alone cannot pass as a native model.

Expected result: You have an editable project and know which output you created. Only a successful native build and package should proceed to a FiveM test.

If it does not work: A missing reference after moving PCs needs the same local source relinked or regenerated. A GLB preview does not preserve every GTA shader, skeleton or native property needed for export.

Which output preserves editable lettering and image layers?

The saved project or project backup. The project keeps the editing data. A PNG contains only the resulting pixels.

Try independently: Explain to another person which file they need to continue editing and which files the server needs.

Jewelry Studio#

Choose a chain and its wearer

Separate the jewelry model from the character used to check its fit.

A downloaded chain is geometry, not a character. It may arrive without a usable GTA skeleton, shader setup or correct scale. Start with one permitted accessory and inspect what was actually imported before planning an export.

Reference body: A character shown beside your jewelry to judge size and placement. It is not part of the jewelry you export.

  1. In Jewelry Studio, choose Browse GTA jewelry for an accessory from your own Legacy installation, or Import jewelry GLB for a model you have permission to use.
  2. Choose the matching male or female fitting body. For an imported chain, use Load GTA fitting body. In the pattern editor, open Fitting reference and use its GTA body loader or your own reference GLB.
  3. Inspect Worn, Front and Side views. Identify whether you are editing a GTA accessory, an imported model, or a Studio pattern before changing its controls.

Expected result: You can identify the chain and the body separately. A locally loaded GTA reference matches the intended wearer.

If it does not work: If the chain fills the view, use the fit/frame control and inspect its scale. A generic imported chain may need preparation in Blender before native export. Find the matching body setup under Learn → Tools & models.

Does importing a chain GLB also provide a GTA character?

No, the fitting body is separate. A GLB contains only the scene exported into it. The app must load the fitting body separately.

Try independently: Point out the model source and body choice without changing either.

Fit jewelry from more than one angle

Adjust placement and recognize clipping before export.

A necklace can look correct from the front while passing through the chest or floating above it. Position changes move it, scale changes its size, and rotation changes its orientation. Make one small change at a time so you know what improved the fit.

Clipping: Two visible surfaces intersecting, such as a pendant passing through a shirt.

  1. Use the worn preview and a representative shirt. Choose Front, then Side, and find the pendant relative to the chest.
  2. Use the controls available for your source to adjust placement and size. For imported jewelry, select the intended part before transforming it. Check the loop around the neck as well as the pendant.
  3. Compare the fit with a different outfit or supported pose. Undo an adjustment that makes the side view worse. Note any motion or attachment checks that still need Blender and FiveM.

Expected result: The jewelry clears the reference outfit in the inspected views. This is a visual fit check, not proof of correct animated skinning.

If it does not work: If moving the pendant also moves unrelated parts, inspect the part selection. If the item clips only while moving, inspect its weights and attachment in Blender and test in FiveM.

Why inspect a necklace from the side?

To check chest clearance and depth. Depth problems can be hidden in the front view.

Try independently: Explain the difference between moving a chain forward and making the entire chain larger.

Prepare a wearable, not just a preview

Identify the required preparation for a chain, watch, ring or other accessory.

The item category controls where a wearable belongs. A necklace, a watch and a pair of glasses do not all share the same component or prop slot. The finished item also needs supported materials, appropriate geometry and an attachment or rig suitable for its body.

Skin weights: Values describing how much each bone influences a mesh vertex during movement.

  1. Save the design and its source. Identify the intended body, jewelry kind and corresponding component or prop target in Pack Builder.
  2. For an imported mesh, follow its preparation and Blender workflow. Check scale, orientation, materials and rig/attachment. Use the actual build diagnostics rather than assuming every GLB is directly convertible.
  3. Run the supported native build and package checks. Keep the diagnostic report. In FiveM, inspect the item while walking, turning and changing clothes before recording an in-game pass.

Expected result: You can explain any remaining preparation and distinguish editor checks from an in-game result.

If it does not work: An item that stays still while the character moves usually needs its rig or attachment investigated. A model that looks metallic in the editor can require different GTA shader settings.

A static preview looks good. What remains unproven?

Animation, attachment and in-game appearance. A static rendering does not exercise the game engine or character animation.

Try independently: Write down three movements you will test and one clothing combination that could cause clipping.

MLO Studio#

Understand a room in 2D and 3D

Inspect editable architecture and understand dimensions before building.

A floor plan describes where a room sits and how large it is. The 3D view shows the generated walls, floor and ceiling. Work in realistic dimensions: a room that looks attractive from a distant camera can still be too small to walk through.

Transform: An object’s position, rotation and scale. Position moves it; scale changes its size.

  1. Open the example house as a learning project. Select a room and inspect its dimensions in the architectural controls.
  2. Switch between Floor Plan and Scene View. Move a corresponding architectural room slightly, then inspect how the other view represents the change.
  3. Undo the move. Check a doorway, wall thickness and floor height from an angle close to a player’s viewpoint.

Expected result: You can identify the same room in both views and restore an experiment using Undo.

If it does not work: If nothing appears, frame the scene and check hidden objects/layers. A free-standing mesh wall is not necessarily part of the architectural room data.

Which operation changes an object’s size?

Scale. Scale changes size; position changes location.

Try independently: Estimate a doorway width before inspecting its actual dimensions. Explain why scale matters for a player.

Connect rooms with real portals

Distinguish a visible doorway from room visibility data.

A hole in a wall lets you see through the geometry in the editor. An MLO portal is separate data that connects room visibility in the game. A building can look complete while its room assignments or portals are missing.

Portal: An opening definition connecting MLO rooms for visibility. It is not a physical door model.

  1. In MLO Studio, open Rooms and Portals. Identify two neighboring rooms and the doorway between them.
  2. Inspect the portal’s room connections, corners and direction. Use the connectivity view to find whether each intended interior route is connected, including the exterior/limbo relationship.
  3. Run the available room and portal diagnostics. Record one issue and its proposed correction, or explain why the selected doorway’s connection is sensible.

Expected result: The portal lies at the intended opening and connects the correct rooms. You understand that visibility still needs a game test.

If it does not work: If a room disappears from an expected viewpoint, inspect connections, portal direction and entity room assignment. Do not fix visibility by randomly adding overlapping portals.

Does cutting a hole in a wall automatically prove MLO visibility is correct?

No, portal data must be checked separately. Geometry and visibility definitions have different jobs.

Try independently: Trace a player’s route from outside through two rooms and name every required visibility connection.

Check collision and build requirements

Find walkable surfaces and distinguish build checks from a game test.

Visible geometry draws the room; collision controls physical contact. A rendered floor can have no collision, and an invisible collision surface can block a doorway. Inspect both before packaging.

Collision mesh: The geometry the game uses for physical contact rather than visual detail.

  1. Open the collision workspace or overlay. Compare each floor and wall with its collision counterpart and check doorway clearance.
  2. Open Build and Export. Run diagnostics and inspect missing tools, room problems, materials and asset dependencies before starting the supported native build.
  3. After a successful build, inspect the generated resource and its manifest. Use a dedicated test server for entry, floor, wall, stairs and visibility checks. Record any checks you have not actually performed.

Expected result: The project has an explained collision plan and an honest checklist of export and in-game requirements.

If it does not work: Falling through a rendered floor points to collision loading or coverage. A successful ZIP operation only proves packaging, not gameplay.

What proves the player can walk on a floor?

A successful in-game collision test. The game must load and use the collision correctly.

Try independently: Find one place where the visible model can be detailed but the collision can stay simple.

Vehicle Studio#

Choose a vehicle with a usable source

Identify the difference between a vehicle preview and a native source.

A vehicle is more than a body mesh. A working GTA vehicle includes hierarchy, bones, materials, collision and configuration. A GLB can be useful for modeling or preview, but does not automatically contain those native relationships.

YFT: A GTA fragment format used for vehicles and other structured assets. A ped skeleton can also use YFT; context matters.

  1. Open Vehicle Studio. Use Load GTA Blista for the supported car from your own Legacy installation, or import a permitted GTA fragment with its matching textures.
  2. Inspect Model overview and the parts hierarchy. Identify the body, a door and a wheel. Hide and show a part to understand the structure.
  3. Record the source kind. If you imported a GLB, inspect the native workshop requirements before expecting a driveable export.

Expected result: You know what source the project uses and can select a vehicle part without confusing it with the whole car.

If it does not work: Missing materials can mean matching YTD files were not supplied. A visual model alone does not establish a native vehicle structure.

Does a car-shaped GLB necessarily contain a working GTA vehicle?

No, native structure and configuration also matter. File extensions and appearance do not create the required internal data.

Try independently: Identify one visible part and one nonvisual requirement for a working door.

Change paint and place a livery

Make a small visual change and verify its placement from several views.

Paint settings and a livery image affect different parts of the material workflow. A logo is placed onto the model’s UV layout. Shared UV regions can repeat a logo, and stretched UVs can distort it.

Livery: Artwork applied to a vehicle’s surface through its material and texture mapping.

  1. Open Customize and change the primary paint to a noticeably different color. Compare Front and Side views.
  2. In Livery, import your own PNG and choose Place logo on car. Select a supported panel, then adjust position, size and rotation.
  3. Inspect the opposite side and nearby seams for unwanted repetitions. Save, reopen the project and confirm the intended change remains.

Expected result: The paint and logo are visible where intended, and you can explain which controls changed each.

If it does not work: If a logo repeats across panels, inspect shared UVs. If native export reports an unsupported material, follow the diagnostic or prepare the source in Blender rather than assuming the preview can be exported unchanged.

What can cause the same logo to appear on two panels?

Shared UV coordinates. Two surface regions can sample the same pixels from a texture.

Try independently: Try a smaller logo with more space around the edge of the panel and compare readability.

Make one handling change and test it

Use a controlled comparison instead of changing many settings at once.

Handling fields interact. Changing acceleration, grip and braking simultaneously makes it hard to tell what helped. Preserve the original values, change one setting conservatively and compare on the same route.

LOD: A level of detail: a different model complexity used at different viewing distances.

  1. In Configuration, inspect donor settings and give the add-on a unique spawn name. Record the original value of the one handling field you plan to change.
  2. Inspect Performance and Build pack for geometry, LOD, collision and missing dependency checks. Resolve build errors before packaging.
  3. In your dedicated FiveM test environment, compare the original and modified behavior on the same route. Check doors, wheels, lighting and distant appearance as well as driving.

Expected result: You can describe one change and the evidence you would use to keep or revert it. Only mark the game test complete after driving it.

If it does not work: A spawn failure may be configuration or naming, not the visible model. Inspect resource logs and manifest/configuration references before changing geometry.

How do you learn which handling change caused a problem?

Change one value and compare under the same conditions. A controlled comparison makes the effect attributable to that change.

Try independently: Write a short driving test with the same vehicle, route and starting conditions.

Script Studio#

Build a command and explain every part

Create a command while understanding its name, callback and execution side.

RegisterCommand connects a typed name to a function. The function is the callback: it runs when the command is used. The resource manifest decides which Lua files run on clients and which run on the server.

Callback: A function supplied to another function so it can be called when an event or command occurs.

  1. Open Make a chat command. Read the generated example before changing its command name and message.
  2. Predict which command the user will type and what output they should see. Run the available practice check and compare it with your prediction.
  3. Open the practice project in Script Studio. Find RegisterCommand and its manifest entry. Explain where the callback begins and ends.

Expected result: You can point to the command name, message and manifest entry instead of only copying a recipe.

If it does not work: If the command does not run in FiveM, confirm the resource is started and the correct file is declared in fxmanifest.lua. The practice environment does not reproduce every game native.

RegisterCommand('hello', ...) registers which chat command?

/hello. The first argument gives the command its name; chat adds the slash.

Try independently: Rename the command and predict the result before running it. Continue with Lua foundations for variables and functions.

Find a bug using evidence

Use a small reproduction, validation and a controlled fix.

A useful bug report describes what you did, what you expected and what happened. A syntax check finds malformed code; it does not prove correct game behavior. Fix one observed problem and repeat the same steps.

Reproduction: The smallest repeatable sequence that demonstrates a problem.

  1. Open a practice resource or a backup copy. Read its manifest and identify the expected entry script.
  2. Run validation and inspect any reported file and line. Compare the actual filename and command spelling with their references before editing.
  3. Make one correction, validate again and repeat the original action. Record any game-dependent checks you could not run locally.

Expected result: You can explain why the correction addresses the reported issue and what remains untested.

If it does not work: A clean validation result does not prove permissions, network events or game natives behave correctly. Use a development server and actual logs for those checks.

What does a clean syntax check establish?

The parsed code has no detected syntax errors. Parsing checks structure, not every runtime or security outcome.

Try independently: Write a three-line report: steps, expected result, actual result.

Understand resources and test safely

Know what belongs in a resource and why the server validates requests.

A FiveM resource groups its manifest and referenced files. Client code controls local presentation; the server must validate actions that affect shared state. A friendly button in a menu is not an authorization check.

Dependency: Another resource or tool that must be available for the selected workflow to function.

  1. Inspect fxmanifest.lua and match each script or UI entry to an actual file in the project.
  2. For a script that changes shared state, identify where the server checks the caller and input. Read the Script security lesson if this is unfamiliar.
  3. Export the resource, read its requirements and test it on a dedicated development server. Keep your editable project backup separately from the deployment copy.

Expected result: You can identify what the resource needs, where it runs and what tests are still required.

If it does not work: A missing dependency needs the documented resource or a compatible implementation. Renaming arbitrary files does not satisfy an API or framework requirement.

Where should a shared-state action validate player permission?

On the server handling the request. A client can make requests independently of the visible interface. The server must enforce the rule.

Try independently: Explain the difference between hiding a button and authorizing an action.

Pack Builder#

Match a wearable to the right slot

Choose the intended body and component or prop category.

A clothing pack needs consistent targets. The wearer, item category, model and textures must agree. A hat and a shirt use different slots; choosing a slot does not convert an incompatible model into that item.

Prop slot: A wearable category such as a hat or glasses, distinct from clothing component slots.

  1. Open Pack Builder and create or inspect a pack. Choose the intended male or female body.
  2. Add a supported item and select its correct component or prop category. Inspect its model and texture inputs.
  3. Review naming and dependency diagnostics before adding more items. Start with one item so failures remain easy to isolate.

Expected result: One item has an explicit target and matching required files. Unsupported or missing inputs remain visible as unresolved requirements.

If it does not work: If the wrong item appears in game, inspect the slot, collection and names before editing the artwork.

Does selecting the hat slot turn a shirt model into a hat?

No, the source must already be appropriate. The target describes the item; it does not remodel or rig its source.

Try independently: Explain how you would classify glasses, a watch and a shirt without guessing a shared slot.

Read build results correctly

Separate missing inputs, conversion results and packaging results.

A build is a sequence. Input validation checks source requirements. Conversion produces native assets through the supported toolchain. Packaging arranges the result as a resource. Each stage can succeed or fail independently.

Native asset: A file encoded in the game’s actual supported format, not merely a renamed preview file.

  1. Run the pack checks and read every blocking diagnostic. Locate missing files or correct the target before building.
  2. Build through the supported workflow. Read the conversion result and check that the expected native files were generated.
  3. Export the resource to a chosen working folder. Inspect the manifest and stream contents and retain the build report.

Expected result: You know which stages passed and can locate the exported files. No stage is assumed successful from a preview alone.

If it does not work: A conversion failure needs its tool log or source fixed; retrying ZIP packaging cannot repair invalid native assets.

What does successfully creating a ZIP prove?

Files were packaged. Packaging does not run the game or prove the content works inside it.

Try independently: List one failure that could occur at each build stage.

Keep a repeatable in-game test record

Record actual results for a wearable on the intended body.

A release decision needs evidence from the intended environment. Keep automated checks separate from observations made in a running FiveM client. Use the same test actions when comparing revisions.

Regression: A previously working behavior that breaks after a change.

  1. Prepare a dedicated test resource and note the app version, body, item and source revision. Follow the FiveM server setup guide if you do not have a test server.
  2. Load the resource and inspect the correct item on the intended character. Check textures, seams, body clipping and several movements.
  3. Record pass, fail or not tested for each check. After a correction, repeat the failing action and recheck behavior that already worked.

Expected result: Your checklist describes tests you actually performed. Untested items remain marked not tested.

If it does not work: If the resource does not load, inspect server logs and manifest paths first. A missing streamed asset and a badly fitting model require different fixes.

You cannot open FiveM today. How should the movement test be recorded?

Not tested. An honest unknown tells the next tester exactly what remains to be checked.

Try independently: Prepare a reusable test list for another user and ask whether they can repeat it without your help.
